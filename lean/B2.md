# B2: build note for the 711 numerics in Lean

This note records how the tier L = 711 numerics are built and what the build costs, so that the check can be reproduced.
The statement and the proof outline are in `README.md` (step B2).

## What is checked

`KeiperComb.N711.combNumerics_711` is `CombNumerics 2000 8 711` for the concrete data, with no hypothesis, and
`KeiperComb.N711.theoremA'_711_numerics` follows from it. `#print axioms` shows only `propext`, `Classical.choice` and
`Quot.sound`. There is no `sorry` and no `native_decide`: the integer checks run by `decide +kernel`.

The modules, all under `KeiperComb/`, none imported by `KeiperComb.lean` (the default target does not build them):

* `Numerics711Core`, `Numerics711Real`, `Numerics711Glue`, `Numerics711Sound`, `Numerics711Sound2`, `Numerics711Sound3`: the exact Gaussian-integer
  checker (`gmul`, `gpowBin`, `checkZeroAll`, `checkBatchFast`) and its soundness proof.
* `Numerics711Zero1`, `Numerics711Chain`, `Numerics711Tail`: the first zero, the chain of nine integer vectors, and the tail bound
  (`Cconst <= 461945/10^7`).
* `Numerics711Cert`: the weights and chain vectors, written by `gen711.py --cert`.
* `Numerics711C00` to `Numerics711C18`: the zero data in 19 chunks (`gen711.py --chunk CI K0 K1 OUT`), each closed by `decide +kernel`.
  C00 and C01 hold 200 zeros, C02 to C17 hold 100, C18 holds the last zero. Together with `Numerics711Zero1` they cover all 2000 zeros.
* `Numerics711AsmGen`, `Numerics711Assembly`: the glue that joins the chunks, and the final integer inequality for each of the nine chain vectors.

## How to build

```
LEAN_NUM_THREADS=1 lake build KeiperComb.Numerics711Assembly
```

Build a chunk alone with `lake build KeiperComb.Numerics711C<CI>`. Do not set `ulimit -v` (Lean maps memory it does not use, and
thread creation fails). Memory is dominated by loading Mathlib (about 6.5 GB); a chunk of 100 zeros peaks at about 8.3 GB and a chunk of 200 at about 10 GB.

The assembly module `Numerics711Assembly` checks the ordering of the 2000 intervals by `decide +kernel` in the same module as the unfolded chunks; it peaks at about 24 GB of RAM (about 40 min wall with one Lean process, on a loaded machine), so build it on a machine with at least 32 GB free.
The zero data cover indices 1..1999; zero 0 (the first zero of the paper) is handled by `Numerics711Zero1`. Zero 400 is in both C01 and C02, which is harmless.

## Why the checker is fast

The first version, with a plain per-vector power, needed about 58 CPU hours for 2000 zeros. Three changes cut this by about two orders of magnitude:

1. The nine chain vectors differ by single increments, so the powers of the zero's quantity for the 16 distinct exponents are built once per zero and shared.
2. `D^e` uses `Nat.pow`, which the kernel accelerates, and the Gaussian powers use square-and-multiply (`gpowBin`).
3. The zeros are split over separate theorems, which bounds memory.

For 2000 zeros as one theorem the memory would be far beyond 40 GB, which is why the data are chunked.

## Notes for rebuilding

* `set` leaves `let` values in the context, and a later cast proof can unfold the literal `2^58`. In the soundness files the values are closed with `clear_value`
  after the `set`s, and `P = E / 2^60` is introduced as an opaque variable by `obtain`.
* A single large theorem may reach the 200000 heartbeat limit; the chain lemma is split into one lemma per leaf, and `combNumerics_711` sets
  `maxRecDepth 20000` and `maxHeartbeats 2000000`.
